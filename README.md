# Shared Counselling

A Django website for a counselling practice. Visitors can explore services, find counsellors by their areas of expertise and session mode, and book an appointment. Practice staff manage profiles, working hours, specialties, and bookings through Django admin.

## Features

- Service pages with topic-based counsellor matching.
- Counsellor directory, profile details, and WhatsApp enquiries.
- Online and in-person booking with availability checks and database protection against duplicate confirmed slots.
- Client confirmation emails, practice CCs, and a separate staff notification.
- Admin-managed content and paired WebP counsellor portraits.
- Sitemap and robots.txt support.

Sessions last 50 minutes, with hourly start times, a two-hour minimum lead time, and a 21-day booking window. Scheduling uses `Asia/Kolkata`. The displayed ₹1,500 fee is informational; there is no payment integration.

## Stack

Python, Django 6, Django templates, vanilla JavaScript and CSS, SQLite locally, PostgreSQL in production, WhiteNoise for static assets, and Gunicorn. Email supports Resend, Brevo, SendGrid through django-anymail, or SMTP. Dependencies are pinned in `requirements.txt`; `runtime.txt` specifies Python 3.13.7.

## Local setup

From the repository root, using Python 3.13:

```bash
python3.13 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

Edit `.env` and replace `SECRET_KEY` with a unique value. Generate one with:

```bash
python -c 'from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())'
```

Then initialize and run the site:

```bash
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Open http://127.0.0.1:8000/ and http://127.0.0.1:8000/admin/. Migrations seed initial service, topic, and counsellor content. The example configuration prints emails to the terminal instead of sending them. Existing environment variables take precedence over `.env`.

## Email configuration

The booking email hook is `core/booking_email.py`, called after the booking is saved in `core/views.py`. This is outbound mail; inbound webhooks and delivery tracking are not implemented.

For Resend, set these environment variables:

```dotenv
RESEND_API_KEY=your-provider-api-key
DEFAULT_FROM_EMAIL=Shared Counselling <bookings@your-verified-domain.example>
BOOKING_NOTIFY_EMAIL=practice@example.com
```

Remove the console `EMAIL_BACKEND` setting from `.env` when enabling real delivery. An explicit `EMAIL_BACKEND` always wins; otherwise selection is Resend, then Brevo (`BREVO_API_KEY`), then SendGrid (`SENDGRID_API_KEY`), then SMTP. Keys are passed to Anymail through its `ANYMAIL` settings dictionary; see the [Anymail Resend configuration](https://anymail.dev/en/v13.0/esps/resend/).

Use a sender authorized by your provider. `BOOKING_NOTIFY_EMAIL` accepts comma-separated inboxes; they receive the confirmation CC and a separate staff email, and the first is the client's reply-to address. Without an override, the application's existing practice inboxes are used.

For SMTP, configure `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, and TLS/SSL settings. Port 465 selects SSL; the default port 587 uses TLS. `EMAIL_TIMEOUT` defaults to 10 seconds. Use the console backend for local work that should not send mail.

If delivery fails, the booking remains saved and the failure is logged. Check application logs, provider credentials, sender authorization, and provider delivery logs before retrying. Mail sends synchronously; there is no background queue or automatic retry. Tests use local or mocked delivery and do not establish live deliverability.

## Configuration and deployment

- `SECRET_KEY`: required, including during builds.
- `DEBUG`: defaults on locally and off when `RENDER` is set; set it explicitly for other production hosts.
- `ALLOWED_HOSTS`: comma-separated hostnames; defaults to localhost and 127.0.0.1. Render domains are added when `RENDER` is set.
- `CSRF_TRUSTED_ORIGINS`: additional comma-separated origins, including the scheme.
- `DATABASE_URL`: selects PostgreSQL with SSL; unset it to use local SQLite.
- Optional `AWS_*` storage settings support remaining file uploads; current counsellor portraits are static assets.

`render.yaml` defines the Render web service and PostgreSQL database. Supply the secret key, email API key, verified `DEFAULT_FROM_EMAIL`, and notification inboxes in the deployment environment. `build.sh` installs dependencies, collects static assets, checks essential files, and runs migrations. Gunicorn starts the WSGI app using the command in `render.yaml` or `Procfile`.

Source assets live in `static/`; `staticfiles/` is generated by `python manage.py collectstatic --noinput`. Admin portrait uploads write to the local static directories, so persistence across deployments requires committing the resulting assets or revisiting portrait storage.

```bash
python manage.py check
python manage.py test
python manage.py makemigrations --check --dry-run
```

Tests cover scheduling, booking validation and mail, admin permissions, portrait handling, and public routes.

## Current limitations

Google/Outlook calendar integration is stubbed: no OAuth, external busy-time lookup, or event creation is implemented. There is no payment processing or client self-service cancellation flow. Confirmation pages use sequential booking IDs rather than authenticated or signed access; access protection needs further work before handling sensitive production booking data.
